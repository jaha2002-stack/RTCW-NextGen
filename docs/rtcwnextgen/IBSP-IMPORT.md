# Импорт разрешённых карт IBSP

Импорт поддерживает отдельные файлы IBSP v46 и v47. Используйте свои карты
или карты, для которых разрешены преобразование и распространение. Python
3.9+ нужен для работы инструментов импорта и компиляции.

```powershell
python tools/import-ibsp.py author.bsp --materials materials.json --resources ./author-assets --out ./converted
python tools/compile-native-level.py ./converted/imported.map --rbdmap ./rbdmap.exe --assets ./converted/assets --map-name imported --out ./native
```

При импорте с AAS передайте `--navigation-def ./navigation.def`, а при
компиляции добавьте `--aas aas48`. Исходные файлы читаются из отдельных
каталогов. Для каждой операции укажите новый каталог вывода.

| Ключ в `materials.json` | Значение |
| --- | --- |
| Имя шейдера из IBSP | Объект с путём `texture` к собственному TGA внутри `textures/` |
| `alpha` | Необязательная непрозрачность больше 0 и не выше 1 |
| `scale` | Необязательные множители исходных UV по U и V |
| `rotate` | Необязательный поворот UV в градусах |
| `$models` | Необязательное сопоставление исходных ссылок на статические модели с готовыми OBJ внутри `models/` |

```json
{
  "fixture/stone": {"texture": "textures/author/stone.tga", "scale": [2, 1], "rotate": 90},
  "fixture/glass": {"texture": "textures/author/glass.tga", "alpha": 0.4},
  "$models": {"models/source/marker.md3": "models/author/marker.obj"}
}
```

Импорт переносит треугольники с координатами и UV, сетки квадратичных
патчей и коллизионные кисти. Имена встроенных моделей и ссылки на текстуры
записываются в нативные MAP и MTR. Файл `import.json` фиксирует SHA-256
входа, версию, сопоставление материалов и непреобразованные записи. Имена
нативных материалов стабильно вычисляются из имён исходных шейдеров. При
замене текстур или параметров MTR исходная геометрия остаётся той же.

Встроенные модели и сопоставленные OBJ можно увидеть через нативный
предпросмотр с параметром `+set com_nativeMapPreview maps/imported`. Для
запуска понадобятся шейдеры DXIL или SPIR-V, соответствующие движку.
Компилятор сохраняет исходные позиции моделей и игровые ключи выбора
сценария. Для игровых сущностей требуются отдельные нативные реализации.

Проверочный вход покрывает помещение, криволинейную прозрачную панель и
две статические модели. Требуют дальнейшей проверки сложные переходы,
ландшафт, специальные типы BSP-поверхностей и поведение игровых сущностей.
