# RTCW NextGen — Stage II Consolidated Scope Correction & Acceptance Directive

## 1. Основание для корректировки

В результате рассмотрения текущего отчёта по P01–P06 установлено, что проект содержит полезные технические наработки нативного игрового движка RBDoom3BFG.

Однако представленные результаты пока не подтверждают наличие функционального конвейера импорта и преобразования исходных уровней и игровых ресурсов.

Настоящая директива уточняет обязательное содержание P01–P06 и заменяет противоречащие ей критерии завершения предыдущих инструкций.

Не изменять основной движок и утверждённую нативную архитектуру.

Не удалять существующие технические наработки.

## 2. Конечная цель проекта

Создать RTCW NextGen на базе RBDoom3BFG с сохранением архитектуры, пространственной структуры, пропорций и узнаваемости исходных игровых уровней, используемых с необходимыми правами и разрешениями.

Использовать нативные возможности RBDoom3BFG для реализации физики, движения, игровой механики, AI, скриптов, аудио и графики.

Точное воспроизведение программной архитектуры id Tech 3 не требуется.

Оригинальный пользовательский интерфейс не является обязательным требованием Stage II.

Современные графические эффекты и полноценная модернизация материалов относятся к последующим этапам.

## 3. P01 — Native Engine Bootstrap

Сохранить текущие достижения Windows x64/DX12 и Linux/Vulkan.

Завершить:

- полноценный нативный игровой режим;
- инициализацию игровых подсистем;
- игровой цикл;
- загрузку игрового мира;
- создание игрока и камеры;
- обработку пользовательского ввода;
- отдельную конфигурацию проекта;
- диагностические журналы.

Предпросмотр геометрии не является эквивалентом полноценного игрового режима.

## 4. P02 — Level Import & Conversion Pipeline

Разделить фазу на три обязательных функциональных блока.

### P02-A — Native Map Compilation

Завершить текущие работы по:

- brushDef3;
- Valve 220;
- PROC;
- CM;
- AAS;
- динамической видимости;
- коллизиям;
- навигации между областями.

### P02-B — BSP Import & Conversion

Проверить наличие фактически реализованного универсального BSP-конвертера.

При его отсутствии и допустимости разработки реализовать конвейер импорта поддерживаемых форматов BSP на основе открытых технических спецификаций и исходного кода.

Обеспечить обработку:

- геометрических поверхностей;
- вершин и индексов;
- brushes и planes;
- patch surfaces;
- координат;
- UV;
- материалов;
- игровых сущностей;
- статической геометрии;
- данных коллизий.

Обеспечить генерацию нативного представления уровня для RBDoom3BFG.

Использовать авторские и свободно лицензированные карты для технического тестирования.

Не обходить установленные ограничения на обработку конкретных коммерческих карт.

### P02-C — Level Geometry & Spatial Fidelity

Обеспечить проверяемое сохранение архитектуры и пространственной структуры импортируемых карт, преобразование которых разрешено.

Проверять:

- стены;
- окна;
- двери;
- полы и потолки;
- лестницы;
- арки;
- колонны;
- помещения;
- коридоры;
- переходы;
- ландшафт;
- расположение архитектурных деталей;
- размеры и пропорции;
- координаты статических объектов.

Не считать простые цветные поверхности или вручную созданную нативную комнату доказательством готовности BSP-конвертера.

## 5. P03 — Material & Asset Compatibility

Не ограничиваться отображением двух тестовых материалов.

Реализовать функциональную архитектуру сопоставления ресурсов:

Source Material Reference
→ Material Mapping
→ Native RBDoom3BFG Material
→ Texture Resources
→ Render Surface.

Обеспечить:

- сохранение привязки материалов к геометрии;
- обработку UV-координат;
- масштабирование и ориентацию текстур;
- прозрачность;
- загрузку совместимых статических моделей;
- обработку трансформаций объектов;
- независимую замену материалов и текстур.

Разработать структуру ресурсов, позволяющую впоследствии подключать новые HD-текстуры и PBR-материалы без повторной конвертации геометрии уровня.

Не начинать полноценную графическую модернизацию.

## 6. P04 — Native Player & Physics

Подключить полноценного нативного игрока RBDoom3BFG.

Обеспечить:

- управление от первого лица;
- ходьбу;
- бег;
- прыжки;
- приседание;
- гравитацию;
- коллизии;
- лестницы;
- наклонные поверхности;
- двери;
- взаимодействие с объектами.

Не считать отдельные трассировки столкновений подтверждением полноценной игровой физики.

## 7. P05 — Native Gameplay & AI

Реализовать необходимые нативные игровые компоненты:

- AI противников;
- навигацию персонажей;
- реакцию на действия игрока;
- базовую механику оружия;
- игровой урон;
- предметы;
- двери;
- триггеры;
- взаимодействия;
- анимации;
- звуковые эффекты;
- сценарии;
- завершение уровня.

Генерация AAS сама по себе не является подтверждением работоспособности AI.

Не требуется точное воспроизведение оригинальных алгоритмов RTCW.

## 8. P06 — Playable Compatibility Baseline

Интегрировать результаты P01–P05.

Подготовить полноценный играбельный прототип с использованием преобразованного уровня при наличии необходимых разрешений.

Проверить:

- запуск;
- загрузку уровня;
- сохранение пространственной структуры;
- отображение материалов;
- перемещение игрока;
- физику;
- AI;
- взаимодействия;
- выполнение игровых сценариев;
- завершение уровня;
- стабильность.

Подготовить Windows x64 Release Candidate с инструкциями по установке, запуску и подключению пользовательских ресурсов.

Не считать успешную компиляцию Windows executable или создание инженерного ZIP подтверждением играбельности.

## 9. Автономность и пользовательская приёмка

Продолжать технически возможную и разрешённую реализацию P01–P06 автономно.

Самостоятельно выполнять промежуточные инженерные тесты, насколько позволяет среда.

Не запрашивать пользовательскую приёмку после каждого промежуточного теста текстур, отдельных поверхностей, коллизий или компиляции.

Пользовательская приёмка должна проводиться после подготовки интегрированного играбельного Release Candidate либо при объективном блокирующем обстоятельстве, требующем участия владельца проекта.

Если ограничения среды не позволяют выполнить конкретный тест, фиксировать это явно.

## 10. Статусы и отчётность

Обновить STAGE_II_ACCEPTANCE_REPORT.md.

Использовать следующие статусы:

- PASS — реализовано и проверено;
- PARTIAL — реализовано частично;
- NOT IMPLEMENTED — не реализовано;
- NOT TESTED — не проверено;
- BLOCKED — имеется объективное блокирующее обстоятельство;
- DEFERRED — перенесено на последующий этап.

Отдельно учитывать:

- готовность универсального конвертера;
- готовность нативного игрового режима;
- готовность конвейера материалов;
- совместимость с конкретными исходными уровнями.

Не присваивать статус PASS на основании тестов, которые не подтверждают соответствующий критерий.

Не объявлять совместимость с оригинальными картами RTCW подтверждённой без фактических проверок.

При наличии сохраняющихся ограничений документировать их точную область и продолжать остальные допустимые работы.

## 11. Запрет перехода к Stage III

Не начинать Graphics Modernization Pass.

Не внедрять дополнительные графические эффекты до завершения Stage II и положительного результата пользовательской приёмки.

Сохранить существующие графические возможности RBDoom3BFG для последующей адаптации.

## 12. Итоговая директива

The current engineering demonstrations are intermediate technical results, not completed Stage II deliverables.

Native map compilation must not be confused with source level conversion.

Material rendering must not be confused with asset compatibility.

Collision traces must not be confused with functional player physics.

Navigation data generation must not be confused with functional AI.

Successful compilation must not be confused with a playable game.

Preserve the approved native RBDoom3BFG architecture.

Continue all technically feasible and permitted implementation tasks across P01–P06.

Prioritize the missing level conversion and asset compatibility components.

Do not substitute the intended project with an unrelated author-created game.

Deliver an integrated playable prototype for final user acceptance, while explicitly documenting any remaining restrictions and unverified compatibility requirements.
